Self-hosted · Multi-user · OpenAPI-first

Glacier Notes Cloud

A self-hosted, multi-user notes web application — an OpenAPI-first monorepo with a Quarkus (Java 21) backend, an Angular frontend, and PostgreSQL persistence.

  • Quarkus 3.37.4
  • Java 21
  • Angular 22.0.7
  • PostgreSQL 18.3
  • Docker Compose

Features

Notes & organization

  • Owner-scoped notebooks, notes, checklists, and labels with archive and trash
  • Sanitized Markdown editing and rendering
  • Ordered checklists with text search and checkbox toggling
  • PostgreSQL-backed full-text search with ownership filters
  • Note version history with preview and restore
  • Image attachments across filesystem, PostgreSQL, or S3-compatible storage, with thumbnails and per-user quotas

Portability & account

  • Portable .glacier.json import/export, desktop-compatible
  • Full account, notebook, or single-note export scope
  • Conflict resolution on import: add as copies, or replace existing by ID
  • Profile and verified email changes, password reset history
  • Self-service account deletion with retention and restoration

Administration

  • User management and invitations
  • Immutable audit event log, exportable as CSV or JSON
  • Instance settings and SMTP status
  • Prometheus metrics on a private management port
  • Environment-gated automated backups with restore verification
  • English and German localization with synced user preferences

Security & operations

  • Optional TOTP second factor, off by default and chosen per account, with single-use recovery codes
  • Step-up verification on sensitive operations, and an administrative reset for a lost authenticator
  • Opaque session tokens with keyed hashes and double-submit CSRF protection
  • Argon2id password hashing and progressive login throttling
  • Ownership isolation enforced at the repository layer — no cross-owner lookups
  • OWASP dependency scanning and Trivy container image scanning in CI
  • Automated log-hygiene enforcement (content, passwords, and tokens are never logged)
  • Named security-attack-simulation tests: session fixation, token replay, path traversal

Setup guide

1. Local setup (for testing)

Regenerate the OpenAPI-generated contracts, install frontend dependencies, then run the backend and frontend side by side. Backend requires a Docker daemon for Dev Services (PostgreSQL) and a few environment variables. 

# From the repo root
./mvnw -pl backend clean generate-sources
cd frontend && npm ci && cd ..

# Terminal 1 — backend, with required env vars
export GLACIER_BOOTSTRAP_TOKEN=local-bootstrap-token-development-only
export GLACIER_SECURITY_SESSION_SECRET=local-session-secret-development-only
export GLACIER_IMAGE_FILESYSTEM_ROOT=/tmp/glacier-notes-dev-images
./mvnw -pl backend quarkus:dev

# Terminal 2 — frontend (proxies /api to :8080)
cd frontend && npm start
# Open http://localhost:4200

2. Enable the second factor locally (optional)

The TOTP second factor is off unless you turn it on, and the two-factor card is not rendered while it is off — so no one is offered a setup that would fail. To exercise it in local development, add two variables to the backend terminal before starting Quarkus. The encryption secret is deliberately separate from the session secret, and startup fails if the feature is on without one of at least 32 non-whitespace characters. 

# Terminal 1 — alongside the variables above
export GLACIER_MFA_ENABLED=true
export GLACIER_MFA_ENCRYPTION_SECRET=local-mfa-encryption-secret-development-only
./mvnw -pl backend quarkus:dev

Then open account settings, enroll with any authenticator app by scanning the QR code, and store the recovery codes it shows you. Signing in afterwards asks for a one-time code as a second stage, and sensitive operations — disabling the factor, regenerating recovery codes, changing an email address, deleting an account — ask again unless you are inside the step-up grace window.

Changing this secret later does not re-encrypt anything: every existing enrollment becomes undecryptable, and the application says so at startup with a count of the affected accounts. For local work, either keep the value stable or clear the enrollments and start over. Administrators can also tune the challenge lifetime, attempt limit, pending-enrollment window, and step-up grace from the admin settings page without a restart — setting the grace to 0 is the quickest way to see a step-up prompt on demand.

3. Install the published release (recommended for real use)

Each tagged release publishes a signed, immutable image to ghcr.io/cracksoldier/glacier-notes-cloud and attaches a versioned Compose file, CycloneDX SBOM, cosign signature bundle, and SHA256SUMS to its GitHub Release. Generate secrets, download the versioned Compose file, optionally verify the image signature, then start the stack — no local build required. 

mkdir -p deployment/secrets
openssl rand -base64 36 > deployment/secrets/database-password.txt
openssl rand -base64 36 > deployment/secrets/bootstrap-token.txt
openssl rand -base64 48 > deployment/secrets/session-secret.txt
chmod 600 deployment/secrets/*.txt
sudo chown 10001:10001 deployment/secrets/*.txt

curl -fLO https://github.com/Cracksoldier/glacier-notes-cloud/releases/download/v0.3.1/compose-v0.3.1.yaml

# Optional but recommended: verify the image was built by this repo's release workflow.
cosign verify ghcr.io/cracksoldier/glacier-notes-cloud:v0.3.1 \
  --certificate-identity-regexp \
    'https://github.com/Cracksoldier/glacier-notes-cloud/.github/workflows/release.yml@refs/tags/v0.3.1' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com

docker compose -f compose-v0.3.1.yaml up -d
# Open http://127.0.0.1:8080

The chown is required, not optional. Compose bind-mounts these files with the ownership they have on the host, and the container runs unprivileged as uid 10001 — a mode-600 file owned by your host account is unreadable inside it. Run the Compose file in a directory that has not hosted another instance of this project, since it would otherwise reuse that instance's database volume.

4. Build the container from source

Only needed when running an unreleased revision or a local modification. Generate secrets, then build and start the full Compose deployment (Quarkus app image plus PostgreSQL). 

cp .env.example .env
mkdir -p deployment/secrets
openssl rand -base64 36 > deployment/secrets/database-password.txt
openssl rand -base64 36 > deployment/secrets/bootstrap-token.txt
openssl rand -base64 48 > deployment/secrets/session-secret.txt
chmod 600 deployment/secrets/*.txt
sudo chown 10001:10001 deployment/secrets/*.txt

docker compose up --build --wait
# Open http://127.0.0.1:8080

# Stop, preserving volumes:
docker compose down
# Stop and delete data permanently:
docker compose down --volumes

5. Running all tests

The full verification loop mirrors CI: backend build and tests, then the frontend contract/lint/build/unit chain, plus the security gates added for the release candidate. 

# Backend — full reactor build and JUnit tests against PostgreSQL
./mvnw verify

# Backend security gates
./mvnw -pl backend org.owasp:dependency-check-maven:check
bash backend/scripts/check-log-hygiene.sh

# Frontend
cd frontend
npm ci
npm run test:repository     # repository/generated-client metadata
npm run check                # Biome format + lint
npm run build:production     # strict Angular production build
npm run test:ci              # Vitest unit suite
npm audit --omit=dev --audit-level=high

# End-to-end (needs a running Compose deployment)
GLACIER_E2E_BASE_URL=http://127.0.0.1:8080 \
GLACIER_E2E_USERNAME=<username> GLACIER_E2E_PASSWORD=<password> \
npm run test:e2e

# The second-factor spec needs GLACIER_MFA_ENABLED=true on the deployment, an
# account reserved for it, and an administrator. Without these it skips silently.
GLACIER_E2E_MFA_USERNAME=<username> GLACIER_E2E_MFA_PASSWORD=<password> \
GLACIER_E2E_ADMIN_USERNAME=<username> GLACIER_E2E_ADMIN_PASSWORD=<password> \
npm run test:e2e

Reserve a dedicated account for the second-factor spec: it enrolls, signs in and out repeatedly, spends a recovery code, and turns the factor off again. It also sets the instance-wide step-up grace to zero mid-run and restores the default afterwards, so it is not safe to run against an instance anyone else is using.
